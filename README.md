# Frontier Benchmark Tracker

**Which benchmarks frontier labs cite in their model releases.**

New benchmarks appear constantly and most of them go nowhere. The ones that matter are the ones frontier labs choose to put in front of the public. This site tracks that choice over time, and only that choice: it records **which benchmarks a lab reported, never how it scored**.

That restriction is the point. A leaderboard tells you who is winning. This tells you what the field currently considers worth measuring, and lets you watch a benchmark rise, saturate, and get quietly dropped.

Live at **https://junkim100.github.io/benchmark-tracker/**

## What it shows

- **A timeline.** One row per lab, scrolling sideways through time, with a mark for every official release and the benchmarks it cited.
- **Benchmark tracking.** Select benchmarks to follow and see how many labs cited each one, year by year. This is how you notice that GSM8K was near-universal in 2023 and has since fallen off entirely.

## Data

Every record comes from an official lab source: the lab's own blog, model card, system card, or its arXiv paper. News coverage and third-party leaderboards are never used. See [SCHEMA.md](SCHEMA.md) for the full contract and the file ownership rules that let many researchers work in parallel.

`data/releases/<lab>.json` is written by hand or by the research automation. `data/benchmarks.json` and `data/timeline.json` are generated by `npm run normalize` and should never be edited.

## Keeping it current

A scheduled workflow researches every third day, searching a seven-day window so that a delayed or dropped run never leaves a permanent hole. Findings are validated against the data contract and committed straight to `main`, which then deploys. Nothing lands unvalidated, records are only ever appended, and a bad entry is one revert away.

It needs an `ANTHROPIC_API_KEY` repository secret. Without it the run fails rather than silently recording nothing. Check the whole path by hand before trusting the schedule:

```bash
gh workflow run Research -f lookback_days=3
```

Two GitHub behaviours worth knowing. Scheduled runs are delayed under load and are not punctual, which the overlapping lookback absorbs. And scheduled workflows in a public repository are switched off after 60 days with no repository activity, so the bot committing its own findings is also what keeps the schedule alive.

## Development

```bash
npm install
npm run dev      # normalize, then serve
npm run build    # normalize, typecheck, bundle
```

The build fails on any data contract breach, so a malformed research record cannot reach the site.
