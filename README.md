# Frontier Benchmark Tracker

**Which benchmarks frontier labs cite in their model releases.**

New benchmarks appear constantly and most of them go nowhere. The ones that matter are the ones frontier labs choose to put in front of the public. This site tracks that choice over time, and only that choice: it records **which benchmarks a lab reported, never how it scored**.

That restriction is the point. A leaderboard tells you who is winning. This tells you what the field currently considers worth measuring, and lets you watch a benchmark rise, saturate, and get quietly dropped.

Live at **https://junkim100.github.io/benchmark-tracker/**

## What it shows

- **A timeline.** One column per lab, running down the page through time, with a mark for every official release and the benchmarks it cited. It also has a table view, because a mark is not something a keyboard can reach.
- **Benchmark tracking.** Select benchmarks to follow and see how many labs cited each one, year by year. This is how you notice that GSM8K was near-universal in 2023 and has since fallen off entirely.
- **A detail panel.** Press the information button on any card to read what that benchmark measures, which versions are counted together with it, and which labs have cited it. Beside the list on a wide screen, in a sheet at the foot of a phone.

## Data

Every record comes from an official lab source: the lab's own blog, model card, system card, or its arXiv paper. News coverage and third-party leaderboards are never used. See [SCHEMA.md](SCHEMA.md) for the full contract and the file ownership rules that let many researchers work in parallel.

`data/releases/<lab>.json` is written by hand or by the research automation, and `data/descriptions.json` by `scripts/describe.mjs`. `data/benchmarks.json`, `data/timeline.json`, `data/release-log.json` and `data/descriptions-site.json` are generated by `npm run normalize` and should never be edited.

`benchmarks.json` is the readable registry: every benchmark with everything known about it. The other three are built for the browser and carry only the fields the interface draws, minified and split so that the parts nothing needs at first paint are not on the path to it.

Most benchmarks also carry a short description saying what they measure, 1,623 of 2,059, and every one comes from a page that was opened and read, recorded alongside it. Most of the registry is obscure: three quarters of it is cited by exactly one lab, and half of it was first cited after the point where a model could be expected to know it. So a benchmark with no findable page is recorded as found nothing rather than described from its name, and the share of the registry in that state is printed on every build.

## Deduplication

Labs spell the same benchmark many ways, and a wrong merge is invisible: it changes `lab_count`, `first_seen` and `labs` for two benchmarks, and nothing downstream can detect it, because a merge is valid by construction. So merging is gated.

`scripts/classify.mjs` folds punctuation, spacing, casing, Greek letters and version notation into one key; `data/aliases.json` carries the rest by hand, including a `_byLab` section for the case where one name means different things to different labs. A name the key rules cannot match goes to `scripts/alias-gate.py`, which asks a differently-trained model two questions and routes the answer to apply, to the suite file, or to review. It fails closed.

`npm run dedupe` runs the other direction. It pairs benchmarks that cite the same source page and puts each pair to the same gate, using the descriptions as the evidence, which is what makes it work: asked on the names alone the gate calls ARC-Challenge a spelling of ARC, and given both descriptions it calls it a version. Proposals land in `data/dedupe-queue.json` for a person to read. Nothing is applied automatically.

## Keeping it current

A scheduled workflow researches every third day, searching a seven-day window so that a delayed or dropped run never leaves a permanent hole. Findings are validated against the data contract and committed straight to `main`, which then deploys. Nothing lands unvalidated, records are only ever appended, and a bad entry is one revert away.

It needs an `ANTHROPIC_API_KEY` repository secret. Without it the run fails rather than silently recording nothing. Check the whole path by hand before trusting the schedule:

```bash
gh workflow run Research -f lookback_days=3
```

Two GitHub behaviours worth knowing. Scheduled runs are delayed under load and are not punctual, which the overlapping lookback absorbs. And scheduled workflows in a public repository are switched off after 60 days with no repository activity, so the bot committing its own findings is also what keeps the schedule alive.

Descriptions are a separate, manual pass over whatever the registry currently holds, because a description read off a page does not go stale the way a release window does:

```bash
gh workflow run "Describe benchmarks" -f limit=12   # a sample across the registry, not the first twelve
```

It only attempts benchmarks with no entry, and refusals old enough to be worth another look, so running it again after a few hundred new benchmarks have accumulated costs only those. A full pass is around four hours; it writes after every batch and resumes where it stopped.

## Development

```bash
npm install
npm run dev      # normalize, then serve
npm run build    # normalize, typecheck, bundle

node scripts/measure.mjs dist   # raw and gzip bytes for everything shipped
```

GitHub Pages gzips text assets on the way out, so `scripts/measure.mjs` reports both columns: the compressed one is what a visitor pays for, the raw one is what the browser then has to parse.

The build fails on any data contract breach, so a malformed research record cannot reach the site.
